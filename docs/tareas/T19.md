# T19 — Autenticación núcleo

## Objetivo
Montar la seguridad del backend: configuración de Spring Security, emisión y validación del
JWT de acceso, login con BCrypt, el usuario actual con sus permisos, `/auth/me`, el cambio de
contraseña y CORS. El resto de la seguridad (refresh, rate limit, locales, PIN, overrides,
usuarios y roles) llega en T21, T22 y T26.

- `backend/src/test/java/cl/minimarket/pos/security/**`

En paralelo corren T17 (audit), T18 (organization, files) y T20 (inventory).

## Qué hacer
1. `SecurityConfig`: sesión stateless, resource server JWT (Nimbus HS256 con `pos.security.jwt.secret`), CORS desde configuración, CSRF desactivado para la API Bearer, públicos solo `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh` (lo implementa T21), actuator `health`/`info` y springdoc en perfiles no prod; todo lo demás autenticado. Entry point y access denied que respondan ProblemDetail `UNAUTHENTICATED` (401) y `ACCESS_DENIED` (403), no el Basic de Boot.
2. **Convención de permisos (la siguen todas las tareas):** las authorities del JWT/usuario son los códigos de permiso de D.1 tal cual, para que `@PreAuthorize("hasAuthority('<código>')")` funcione. El `sub` del JWT es el id numérico del usuario y el principal implementa `UserIdentity` (L-03), para que `StoreContextFilter` lo reconozca.
3. `POST /api/v1/auth/login` (usuario + contraseña, BCrypt costo 12, sin terminal): responde `TokenResponse` según F.3 (access token, expiración, `mustChangePassword`, `scope`). Contraseña errónea → 401 `INVALID_CREDENTIALS`; usuario inactivo o bloqueado según F.1. El refresh token, la cookie y el bloqueo por intentos son de T21: deja el punto de extensión documentado.
4. `CurrentUser` / `PermissionEvaluator` que considere el local activo (`hasPermission(code, storeId)`; un usuario con `security:store:all-access` accede a todos).
5. `GET /api/v1/auth/me` [G] y `POST /api/v1/auth/me/password` [G] con `@GlobalEndpoint`. Cambiar la contraseña limpia `must_change_password`.

## Criterio de terminado
- PI: login correcto con el admin de la semilla (el hash de prueba `AbstractIntegrationIT.TEST_ADMIN_PASSWORD_HASH` corresponde a la contraseña de desarrollo `DevAdmin#2026`; trabaja sobre una copia del admin o restaura su estado, porque la BD es compartida), login con contraseña errónea → 401 `INVALID_CREDENTIALS`, `mustChangePassword` = true en el primer login del admin y false tras cambiar la contraseña.
- PI: sin token → 401 `UNAUTHENTICATED` en formato ProblemDetail; token válido sin el permiso → 403 `ACCESS_DENIED`; un endpoint global con token válido no exige `X-Store-Id`.
- `OpenApiExportIT` sigue en verde (springdoc accesible en el perfil de prueba).
- Verificación de `AGENTS.md` §4 en verde.
